## 2. AI 参与的环节与验证方式

| 环节 | AI 做了什么 | 怎么验证 |
|---|---|---|
| 读题与选题 | 拆解三道题的交付物与隐含考点，对照作者已有项目给出选题建议 | 人工决策选第 1 题 |
| 读接口文档 | 从扶摇 `llms-full.txt` 整理可用接口、字段、限流与错误码 | 与文档原文逐项核对路径和字段名；不确定的（下载链接返回结构）做成兼容处理并加测试 |
| 口径字典 | 起草 14 个概念、26 个指标的口径方案 | 契约测试：每个方案的条件必须合法、每个概念恰好一个推荐项、同义词不跨概念；人工审口径（见第 3 节） |
| 引擎与解释 | 编写三态判定、分组、漏斗、敏感度、证据卡 | 一致性测试：漏斗末项 = 入选数；“去掉第 i 条多出 N 只”与真正去掉后重跑一致；曲线当前点 = 入选数 |
| 数据管道 | 编写扶摇客户端、快照构建、复权计算 | MockTransport 测试限流、业务错误、重试上限；手算除权日收益率核对；送转单位体检 |
| 前端 | 编写页面 | 在浏览器里逐步走完主链路，检查渲染与交互 |

## 3. 开发中发现并修正的问题

以下都是本项目开发过程中真实出现、经测试 / 评测 / 人工审查发现后修正的，修正后有对应测试兜底。

| # | 问题 | 怎么发现 | 修正 |
|---|---|---|---|
| 1 | “破净”被放进“低估值”概念，默认方案是 PE ≤ 15，语义错了 | 人工审口径 | 改为固定说法：破净 = 市净率 0～1 倍 |
| 2 | “现金流好”方案用 `净利润增速 > −100%` 冒充“净利润为正”，逻辑不成立 | 人工审口径 | 改为 `销售净利率 > 0` |
| 3 | “大于 15%”被解析成 `≥ 15`，与“不低于”混为一谈 | 人工审解析结果 | 严格区分 `<` `<=` `>` `>=` 四类措辞，加测试 |
| 4 | “明天会涨停”只截到“明天会涨”，拒绝理由对、片段不完整 | 浏览器点验 | 正则备选项按长度排序 |
| 5 | “剔除 ST 和次新股”漏掉次新；改写时还撞上 Python 正则不支持变长回看 | 评测集 `excl` 用例失败 | 改为代码里向前查找剔除动词，按出现顺序处理 |
| 6 | 同一概念出现两次（“高速增长的成长股”）在页面重复成两张卡 | 评测输出 | 概念片段按概念去重 |
| 7 | 中报 ROE 是半年数据，直接和“ROE 15%”比较会系统性偏严 | 人工审口径（领域知识） | 明确年化 = 原值 × 2，证据卡同时展示原值 |
| 8 | 三季报披露期混用不同报告期，同一条件比较的不是同一段时间 | 人工审口径（领域知识） | 统一用 2026 中报并在页面写明 |
| 9 | 估值类行业中位数把亏损公司的负 PE 算进去，中位数被拉低 | 人工审口径 | 估值类只统计正值，可比公司不足 5 家记为缺失 |
| 10 | 监控“移出原因”显示成条件编号（“经营改善：c1”），用户看不懂 | 人工审页面文案 | 改为完整条件描述 |
| 11 | 日更时间判断写成“小时 ≥ 16 且分钟 ≥ 30”，17:10 会被跳过 | 代码审查 | 改为比较 (时, 分) 元组 |
| 12 | 演示数据的交易所分配表达式写乱，三分之一是北交所 | 代码审查 | 重写为明确规则 |
| 13 | 右栏“条件变化的影响”过长，把结果表挤到很下面 | 浏览器点验 | 限高并在框内滚动 |
| 14 | 原设计直接用扶摇财务指标里的营收、净利润同比字段，接上真实数据后发现这两个字段全为空 | 接口探测（抽查 8 只 × 3 个报告期） | 改用利润表原始金额自算增速，还因此拿到了真实的单季数据和披露日 |
| 15 | 未发布的报告期，扶摇返回 5003（数据源不可用）而不是文档里的 3002，原代码会把它当故障反复重试并终止构建 | 接口探测 | 单只股票没数据记为缺失；只有鉴权错误或错误率超 2% 才终止 |
| 16 | `.gitignore` 里的 `data/` 把代码目录 `mingshai/data/` 也忽略了，线上首次部署启动失败 | 部署日志 | 改为只忽略根目录 `/data/`，并在干净克隆里重跑全部测试 |
| 17 | 界面初版：夜间对比度不够、说明文字太长、窄屏排版挤 | 作者试用反馈 | 重调夜间配色、全站文案精简、手机 / 平板 / 宽屏分别适配，加日间 / 夜间切换 |
| 18 | 结构化输出的 Schema 把 `null` 写进枚举，Claude 接口直接 400，所有请求退回规则解析 | 接上真实 Key 后首次调用 | 可空枚举改成 `anyOf`，加回归测试，防止再写错 |
| 19 | AI 解读提到“60 日”“120 日”，被数字守门器当成没有出处的数字拦下 | 本地实测 | 守门规则改为“解读里的每个数字都必须出现在交给它的事实材料里”，指标名里的天数自然有出处，没有放松把关 |
| 20 | AI 解读说“条件里没有市值限制，大盘股没被筛选”，实际上股票池已经限定为沪深 300 | 人工核对解读内容 | 原因是事实材料漏了股票池；把股票池每一步的只数写进材料后，解读如实说明“大盘股用沪深 300 代理” |
| 21 | 大模型评测首轮 31/33，两条“失败”复核后是评分太窄：“破净”被映射到低估值的“市净率 1 倍以下”方案（与写明数字等价）；“越来越赚钱”被理解成“盈利能力在变强” | 逐条复核评测输出 | 评分改为比较编译后的条件；“越来越赚钱”一条接受两种理解并写明理由。没有为了凑分去放宽其他用例（见 4.1） |
| 22 | 演示视频初版字幕被裁掉、画面发糊：无界面 Chrome 的截屏流按 CSS 像素出帧，且窗口比设定的视口矮 | 逐句截帧人工检查 | 窗口直接开到 1920×1080、按原生分辨率出帧，页面内容放大 1.2 倍，叠加层不放大 |
| 23 | 配音读音：whisper 回听发现“一句话选股”句末声调偏、“Claude”被听成“Cloud” | 本地 whisper 转写比对 | 调整句式让“选股”不在句末；朗读用“克劳德”，字幕仍写 Claude API |
| 24 | 两段等接口的场景（查茅台、合规拒绝）旁白先说完、画面后到 | 逐句截帧检查 | 拆成两句：先边说边操作，等画面出来再说后半句；不写死具体数字，数据刷新后也不会对不上 |
| 25 | 合规拒绝要等大模型返回（约 7 秒），而这类句子根本不需要模型 | 录视频时发现的空等 | 合规前置：整句只有预测 / 承诺 / 建议类内容时，规则层直接拒绝，不调用大模型（加测试 `test_pure_refusal_never_reaches_llm`） |

## 4. 产品内大模型的验证

### 4.1 意图解析评测（`eval/run_eval.py`，33 句）

| 解析方式 | 通过 | 标准说法 | 口语 | 英文 |
|---|---|---|---|---|
| 规则 | 25/33（76%） | 25/26 | 0/6 | 0/1 |
| 大模型 Claude `claude-opus-5-5` | 32/33（97%） | 25/26 | 6/6 | 1/1 |

- 规则解析做不到、大模型做到的，正是口语（“股价别太折腾”“利润都是真金白银收回来的”）和英文（“low PE, high dividend”）。
- 大模型唯一没过的一条：“PE 在 10 到 20 倍之间、不要亏损的”，它把“不要亏损”理解成**净利率 > 0（上半年不亏）**，
  标注是 **PE(TTM) > 0（近 12 个月不亏）**。两者统计期不同，所以保留为“未过”；产品上这条条件会显示在第 3 步，用户可以直接改。
- 大模型输出不是完全确定的：同一批用例两次运行，未过的用例不完全相同（首轮 31/33）。所以每次解析都有规则解析对照（页面“对照：规则解析结果”），
  并且解析结果只是条件草稿，执行前必须经过用户确认和守门器。
- 结果文件：`eval/results/20261015-0157.json`（首轮）、`eval/results/20261015-0201.json`（评分改为比较编译后条件之后）。
- 单次解析耗时约 5～8 秒（`effort=low`），系统提示词设置了缓存断点。

评分口径：概念集合、写明数字的条件（指标 + 数值 + 方向）、股票池、行业、拒绝与无法识别片段数、剔除项，每条用例只查它写明的项；
另查“没有误拒”（不该拒绝的句子里不能出现拒绝片段）。

### 4.2 守门器

- 大模型输出目录外的概念、越界数值、结构不合法的片段，整条拦下并在页面“守门器拦下了 AI 的 N 条输出”里展示原因（测试 `test_llm_out_of_catalog_is_blocked`）。
- 白话解读：文中每个数字都必须能在引擎结果里找到（千分位、百分比、四舍五入都算对上），且不能出现预测、承诺或买卖建议；否则整段丢弃（测试 `test_number_guard` `test_compliance_guard`）。

### 4.3 调用成本与总额度

- 实测（2026-10-15）：一次解析约 5,000 输入 token（口径目录和行业表，可缓存）加约 500 输出 token。
  首次写缓存约 0.034 美元，5 分钟内再次调用命中缓存约 0.012 美元（Opus 5.5：输入 4、输出 20、缓存读取 0.2 美元 / 百万 token）。
- 线上设了总额 5 美元的硬上限（`mingshai/budget.py`）：调用前按最坏情况预留（输入按缓存写入价、输出写满 `max_tokens`、
  再算一次被拒后换模型重答），调用后按 usage 记实际花费；超时等不知道是否已计费的情况按预留额度记。
- 剩余额度不够一次最坏情况调用（约 0.4 美元）时永久切断并删除服务器上的 Key，所以累计花费不会超过 5 美元。
  切断后解析退回规则，白话解读改用模板摘要，页面写明原因。

## 5. 仍然需要人工判断的地方

- 口径方案本身（什么叫“经营改善”）是产品决策，字典里每个方案都有白话说明，用户可以在澄清面板换掉。
- 行业中位数的分组粒度依赖同花顺行业层级，自动选覆盖率 ≥ 80% 的最细一级，构建日志里记录了各级的组数和覆盖率。
